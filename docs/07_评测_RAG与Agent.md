# 07 评测、RAG 与 Agent

对应 PDF：物理页 143-163。本章从“会输出文本”推进到可测量、可追溯、有失败边界的系统。

## 1. 先分清评测对象

| 对象 | 典型指标 | 不能单独回答的问题 |
|---|---|---|
| 语言模型 | NLL、困惑度、任务准确率 | 应用是否引用正确、是否及时 |
| 检索器 | Recall@k、MRR、nDCG | 生成器是否忠实使用证据 |
| RAG 端到端 | 答案正确率、忠实度、引用正确率 | 单凭总分难定位哪一层失败 |
| Agent | 任务成功率、工具错误率、步骤/成本/延迟 | 一次漂亮演示是否稳定 |

评测设计要先明确对象，否则“答案错了”无法判断是模型、检索、数据还是控制代码的问题。

## 2. 困惑度

平均负对数似然为 `NLL` 时：

\[
PPL=\exp(NLL)
\]

直觉上，它表示模型在每一步像是在多少个等概率候选中犹豫。注意：不同 Tokenizer 会改变序列长度和词表，困惑度不能不加说明地横向比较。

## 3. RAG 的完整数据流

```text
离线：文档 -> 切块 -> 向量化 -> 索引
在线：问题 -> 向量化 -> top-k 检索
                       -> 上下文 + 问题 -> 生成
                       -> 答案 + 来源
```

RAG 通常不更新模型参数。它把外部资料放入上下文，改善可追溯性和知识更新速度，但不会自动消灭幻觉。

本项目为了让每条断言都能由程序核对，使用“抽取式回答层”代替在线生成模型：它从最高相关文档复制句子并附上来源。这个基线展示完整的检索、拒答、引用和评测边界，但不代表真正的 LLM 生成能力。

## 4. Tiny RAG 实验

运行：

```powershell
.\.venv\Scripts\python.exe .\experiments\09_tiny_rag.py
```

实验只用仓库内 `data/rag_documents.json`，流程是：

1. 读取文档和稳定 ID。
2. 英文转小写 token；中文使用字符 unigram 与 bigram。
3. 计算 TF-IDF 和余弦相似度。
4. 用余弦相似度检索 top-2。
5. 相关度低于阈值时明确回答“资料不足”，不生成虚假来源。
6. 相关度足够时，从证据中抽取句子并附加 `[document-id]`。
7. 用严格的规范化包含关系检查每条回答是否受引用文档支持。
8. 在 6 个可回答问题和 2 个资料外问题上分别评测检索、拒答、支持性与端到端成功。

余弦相似度：

\[
\cos(a,b)=\frac{a\cdot b}{\lVert a\rVert\lVert b\rVert}
\]

预期四项指标都是 100%，并逐题打印检索分数、答案、来源和支持率。这里的数据集很小且人工设计，满分只证明教学管线满足这些样例，不代表生产质量。

## 5. Recall@k

若每个查询只有一个标注相关文档：

\[
Recall@k=\frac{\text{正确文档进入前 k 的查询数}}{\text{查询总数}}
\]

k 越大，Recall 往往越高，但交给模型的无关上下文也可能更多、成本更大。不要只把 k 调到文档总数来“刷满分”。

## 6. RAG 失败矩阵

| 检索 | 生成 | 诊断 |
|---|---|---|
| 对 | 对 | 正常成功 |
| 对 | 错 | 生成未忠实使用证据、提示或模型问题 |
| 错 | 对 | 可能靠参数记忆猜中，不能算有证据成功 |
| 错 | 错 | 先改索引、切块、查询和检索器 |

必须保存 top-k 片段与分数，才能做这个分类。

## 7. 文档切块的取舍

- 太大：一个向量混合多个主题，检索不精确，输入 token 多。
- 太小：语义和上下文断裂，答案可能缺条件。
- overlap：减少跨边界信息丢失，但增加索引量和重复召回。

练习：把一个长段落分别按 50、100、200 字切块，标注 5 个查询，比较 Recall@k 和上下文长度。

## 8. “有来源”仍不等于“来源支持答案”

至少检查：

1. 引用 ID 是否真实存在。
2. 引用片段是否包含回答所需事实。
3. 回答有没有加入片段未支持的断言。
4. 多个来源冲突时是否表达不确定性。
5. 资料不足时是否能回答“不知道”。

## 9. Agent 是系统，不是单个提示词

最小工具循环：

```text
用户目标
  -> 模型提出结构化工具调用
  -> 程序校验工具名和参数
  -> 在权限边界内执行
  -> 结果写回状态
  -> 模型决定继续或给最终答案
```

必要组成：模型、工具、状态、控制循环。生产系统还需要权限、超时、幂等、审计、预算、终止条件和人工确认。

### 最小 Agent 练习

运行仓库中的确定性基线：

```powershell
.\.venv\Scripts\python.exe .\experiments\11_local_agent.py
```

不接在线模型也能完整设计状态机：

- 规则规划器把任务路由到 `knowledge_search(query)` 或 `calculator(expression)`。
- 计算器用 Python AST 白名单解释基础算术，不使用 `eval` 或 shell。
- 控制器设置最大步数；每一步都保存 action、observation 和错误。
- 工具名必须来自白名单。
- 未知工具、工具异常和达到最大步数都有不同的停止状态。

实验必须同时通过正常算术、带引用检索、资料外拒答、未知工具拦截、除零错误和无限规划截断。规则规划器只是为了看清控制循环；换成 LLM 后，工具校验、权限和终止逻辑仍应由确定性程序负责。

## 10. 消融实验

至少做一个：

- 关闭检索，只给问题，比较事实回答。
- top-k 从 1 改 2/4。
- 去掉 ID，观察引用是否更容易编造。
- 去掉“资料不足则不知道”，记录无证据断言。
- 替换一个冲突文档，观察系统是否发现矛盾。

一次只改变一个设置，并保存相同查询集上的结果。

## 11. 出门测

1. Recall@5 很高但答案忠实度低，下一步应检查哪一层？
2. 为什么 RAG 不等于把知识永久写进模型？
3. 一个 Agent 可以执行删除操作时，哪些步骤必须由确定性程序而不是模型保证？
4. 设计一个“答案恰好正确但证据错误”的反例，并说明为何不能算 RAG 成功。
5. 为什么“模型承诺最多调用三次工具”不能替代控制器的 `max_steps`？
